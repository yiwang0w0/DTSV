## §0 一句话目标

把现在「`isBr` 二元硬分叉 + 上帝文件里塞 `if (gametype===X)`」的隐式模式逻辑，提炼成两层**声明式描述符**：

1. **mode 描述符**（`game_modes`）—— 正交规则开关集（PvP 开/关、胜负判定、奖励倍率、录像、天梯…），对应 dts `system.config.php` 的 by-gametype 白名单数组思路（`$pve_ignore_mode` / `$teamwin_mode` / `$elorated_mode`…，`include/modules/core/sys/config/system.config.php:68-97`），但落地为 DTSV 原生 JSONB 行 + ID 引用。
2. **副本（dungeon）描述符**（`dungeon_templates` + 引用桥接表）—— 专属 NPC 集 / 掉落 / 胜负条件 / 战斗修正，对应 dts `instance5-9` 用一组钩子 override 改出新玩法（`include/modules/extra/instance/instance9_rush/main.php:6-60` 覆盖 `get_npclist/get_shopconfig/get_itemfilecont/...`），但落地为「描述符行 + 现有钩子点读它」，绝不照搬 `eval(import_module(...))` / `if (19==$gametype)` / 文件加载。

**范围只做 搜打撤 PVE + PVPVE。** 不复制 dts 13 模式广度。孤立的 `br_match*` 第二实现按 `docs/timejump-br-design.md:50` 自记 teardown 一并清掉。

### 1.2 痛点（要本子系统解决的）

- **没有「模式 / 副本描述符 + 钩子覆盖点」中间层。** 模式区别是**隐式**的：`joinRoom` 用 `const isBr = gamevars.br?.enabled === true || !hasChamberRaid`（`gameActions.js:2425`）做二元判据，整局走 BR 还是旧 chamber 全靠这一行。
- **PvP 无模式级闸门。** `resolvePlayerAttackAction`（`gameActions.js:1862-1971`）只校验「同扇区 / 同地图 / 活着」，**没有任何「本模式是否允许 PvP」的判定** —— 想做「PVE 局禁 PvP」只能在这个函数里塞 `if`。

- **孤立第二实现 `br_match*`。** `/br` 独立页 + `br_matches/br_match_events/br_match_players/br_match_room_state` 四表（`docs/timejump-br-design.md:119-122`）是 BR 并入 `/game` 之前的旧实现，已 dormant，自记 teardown（`docs/timejump-br-design.md:50`）。运行端真相已全在 `rooms.gamevars.br`。

## §2 数据模型

> 命名遵守红线：引用一律 ID + 引用完整性（避免 dts「改名即断链」的名串匹配）。所有新列 DEFAULT 中性 ⇒ 现有局逐值不变。所有 migration 幂等（`CREATE TABLE IF NOT EXISTS` / `pg_constraint` 检测后 ADD / `CREATE OR REPLACE` / BEGIN..COMMIT），不部署（主代理审后用 postgres MCP 跑），沿用 `scripts/phase-38-npc-placement.sql` 模式。

### 2.1 `game_modes` — 模式描述符（正交规则开关集）

```sql
CREATE TABLE IF NOT EXISTS game_modes (
  id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  mode_key     text   UNIQUE NOT NULL,        -- 业务键(代码/descriptor 引用)：'pve' | 'pvpve'
  name         text   NOT NULL,               -- 玩家可见显示名："纯净撤离(PVE)" / "对抗撤离(PVPVE)"
  description  text   DEFAULT '',
  -- ── 正交规则开关（= dts by-gametype 白名单数组的 DTSV 原生化；每个开关一列，默认=现状行为）──
  pvp_enabled        boolean NOT NULL DEFAULT true,   -- false ⇒ resolvePlayerAttackAction 拒绝(PVE 禁同屏真人互殴)
  win_condition      text    NOT NULL DEFAULT 'last_alive', -- 'last_alive'|'all_extract'|'any_extract'|'dungeon_clear'
  ladder_rated       boolean NOT NULL DEFAULT false,  -- 是否计天梯(对齐 dts $elorated_mode)
  record_replay      boolean NOT NULL DEFAULT false,  -- 是否录像(对齐 dts $replay_ignore_mode 取反)
  reward_mult        real    NOT NULL DEFAULT 1.0,    -- 撤离奖励倍率(PVPVE 风险高→可调高)
  allow_dungeons     boolean NOT NULL DEFAULT true,   -- 本模式能否进入副本(dungeon_templates)
  enabled            boolean NOT NULL DEFAULT true,
  rule_overrides     jsonb   NOT NULL DEFAULT '{}'::jsonb, -- 前向扩展位：未来新开关先进 JSONB 再视稳定度升列
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()  -- BEFORE UPDATE 触发器(沿用 phase-38 范式)
);

CHECK win_condition IN ('last_alive','all_extract','any_extract','dungeon_clear');
CHECK reward_mult >= 0;
```

**绑定到局：** `rooms` 已有 `gametype int default 0`（`roomState.js:400`，BR=20）。新增软引用列（不改 gametype 语义，避免动现有 lifecycle）：

```sql
ALTER TABLE rooms ADD COLUMN IF NOT EXISTS mode_key text;  -- NULL ⇒ 走当前默认行为(向后兼容)
```

> 为何不直接 FK `rooms.mode_id → game_modes.id`？局是高频写行、历史归档行不能被删模式连累；用 `mode_key`（业务键软引用，同 chamber/placement 软引用范式）+ 运行时 `resolveMode(mode_key)` 兜底缺失→中性默认。归一函数永不抛。

**两行 seed（范围铁律：只 PVE+PVPVE）：**

```sql
INSERT INTO game_modes (mode_key,name,pvp_enabled,win_condition,reward_mult) VALUES
  ('pve',   '纯净撤离',  false, 'all_extract', 1.0),
  ('pvpve', '对抗撤离',  true,  'last_alive',  1.2)
ON CONFLICT (mode_key) DO NOTHING;
```

### 2.2 `dungeon_templates` — 副本描述符

```sql
CREATE TABLE IF NOT EXISTS dungeon_templates (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  dungeon_key   text   UNIQUE NOT NULL,          -- 业务键："eden_boss_raid"
  name          text   NOT NULL,
  description   text   DEFAULT '',
  mode_key      text   NOT NULL DEFAULT 'pve',   -- 副本默认归属哪个模式(软引用 game_modes.mode_key)
  -- ── 胜负条件(副本级·覆盖 mode.win_condition)──
  clear_condition jsonb NOT NULL DEFAULT '{}'::jsonb,
  --   形状(JS 纯函数 evaluateDungeonClear 解释·禁 eval)：
  --   { "type":"kill_npc",      "npc_id":42 }                         -- 击杀指定 boss = 通关
  --   { "type":"kill_all",      "npc_ids":[42,43] }                   -- 清掉一组 = 通关
  --   { "type":"survive_phase", "phase":6 }                           -- 活到相位 N = 通关
  --   { "type":"protect_npc",   "npc_id":9, "until_phase":5 }         -- 保护目标存活到相位 = 通关
  --   { "type":"reach_room",    "br_room_id":77 }                     -- 抵达指定房 = 通关
  fail_condition  jsonb NOT NULL DEFAULT '{}'::jsonb,   -- 同形状·满足即判失败(可空)
  -- ── 战斗修正(副本级·乘区·DEFAULT 中性 ⇒ 不改副本则数值不变)──
  combat_mods   jsonb NOT NULL DEFAULT '{}'::jsonb,
  --   { "enemy_atk_mult":1.0, "enemy_hp_mult":1.0, "player_heal_mult":1.0, ... } 缺省即 1.0
  -- ── 奖励(通关额外发放·接 endings.rewards 同范式 [{name,quantity}])──
  clear_rewards jsonb NOT NULL DEFAULT '[]'::jsonb,
  ending_key    text   NULL,                     -- 通关触发哪个 endings.key(软引用·复用现有结局管线)
  enabled       boolean NOT NULL DEFAULT true,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

### 2.3 `dungeon_npc_sets` — 副本↔专属 NPC 投放（引用桥接）

副本「专属 NPC 集 + 固定 boss 房」**不另造投放算法**，而是复用 §1.1 的 `npc_placement_rules` —— 副本只是「一组 placement 规则的命名集合 + 一个固定房位」。

```sql
CREATE TABLE IF NOT EXISTS dungeon_npc_sets (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  dungeon_id    bigint NOT NULL REFERENCES dungeon_templates(id) ON DELETE CASCADE,
  -- 复用敌人投放规则(NPC 为中心)：副本激活时把这些规则并入本局 allocateRoomNpcs 输入
  placement_rule_id bigint NOT NULL REFERENCES npc_placement_rules(id) ON DELETE CASCADE,
  is_boss       boolean NOT NULL DEFAULT false,   -- true ⇒ 标记为通关判定关注的 boss
  fixed_room_id integer NULL,                      -- 非空 ⇒ 固定投放到这间房(软引用 br_rooms.room_id·覆盖规则的随机候选)
  notes         text   NULL,
  UNIQUE (dungeon_id, placement_rule_id)
);
CREATE INDEX IF NOT EXISTS dungeon_npc_sets_by_dungeon ON dungeon_npc_sets(dungeon_id);
```

> **固定 boss 房**：`fixed_room_id` 非空时，`allocateRoomNpcs` 的副本分支跳过加权采样，直接把该 npc push 到指定房（`max_per_room` 仍守 1）。`fixed_room_id` 软引用（不建 FK，沿用 phase-38 解耦房增删）。

### 2.4 RLS / 索引

- 三张内容表（`game_modes` / `dungeon_templates` / `dungeon_npc_sets`）：与现有内容池（`chamber_templates` / `npc_placement_rules`）同策 —— **读：authenticated 可 SELECT；写：仅 service-role / admin**（运行端用 service-role client，admin authoring 走已有 `/api/admin/*` 服务端校 `isAdmin`）。沿用现有池的 RLS 模式即可，不新发明。
- 索引：`game_modes(mode_key)`/`dungeon_templates(dungeon_key)` 已由 UNIQUE 隐式建；`dungeon_npc_sets(dungeon_id)` 显式建（热点：副本激活时按 dungeon_id 拉规则集）。

## §3 后台编辑（在 01 内容引擎里 authoring）

- **列表**：mode_key / name / pvp_enabled badge / win_condition / 启用。
- **编辑表单**：name + description；正交开关用 checkbox/select（`pvp_enabled` 勾选框、`win_condition` 下拉、`ladder_rated`/`record_replay` 勾选、`reward_mult` 数字）。

### 3.2 `🏰 副本` tab（DungeonsTab）

- **基本信息**：dungeon_key / name / description / `mode_key` 下拉（从 `game_modes` 拉）。
- **胜负条件构建器**：`clear_condition` / `fail_condition` 用「type 下拉 + 动态字段」表单（type=`kill_npc`→显示 NPC 下拉，type=`survive_phase`→显示相位数字，type=`protect_npc`→NPC 下拉+相位）。**NPC 一律下拉选 `npc_pool` 行存 `npc_id`**（红线：ID 引用，非名串）。
- **专属 NPC 集**（`dungeon_npc_sets`）：从 `npc_placement_rules` 多选已存规则并入本副本；每条可勾 `is_boss` + 选 `fixed_room_id`（复用 `CandidateRoomPicker` 单选模式）。
- **战斗修正**：`combat_mods` 4 个乘区数字框，默认 1.0，旁注「1.0 = 不变」。
- **奖励 / 结局**：`clear_rewards` repeater（道具下拉+数量）+ `ending_key` 下拉（从 `endings` 拉，软引用复用结局管线）。
- **校验**：保存前跑「干跑校验」——`clear_condition.npc_id` 必须指向存在的 `npc_pool` 行且该 NPC 在某条并入的 placement 规则里（否则警告「这个通关 boss 永远不会刷出」）；`combat_mods` 全 ≥ 0。
- **预览**：模拟「本副本：从哪个模式进 → 专属敌人 N 条规则 → 通关条件一句话 → 通关发什么」的卡片。

## §4 运行端集成（DTSV 哪个文件怎么消费）

> 红线：**建在 02 钩子管线之上**。本子系统不新发明回合循环，只在已有钩子点「读描述符 → 取开关/条件」。所有读取走归一函数（缺配置→中性默认，永不抛）。

### 4.1 模式归一（新增 `src/lib/server/modes.js`）

```
resolveMode(client, room, gamevars) → { mode_key, pvp_enabled, win_condition, reward_mult, ... }
```
- 读 `room.mode_key`（缺失→按 `gamevars.br?.enabled` 推：BR 局默认 `pvpve`，旧 chamber 局 `pve`）→ 查 `game_modes` 缓存（同 `_allItemsCache` 全局缓存范式，`gameActions.js:294`）→ 缺失行回落硬编码中性默认（`pvp_enabled:true` = 现状）。
- **缓存**：mode 行极少（2 行），进程级缓存 + TTL，零额外 DB 往返热路径。

### 4.2 PvP 闸门（02 钩子点：攻击前置守卫）

`resolvePlayerAttackAction`（`gameActions.js:1862`）开头、现有「同扇区 / 同地图」校验之后，加一句钩子读取：

```js
const mode = await resolveMode(client, room, gamevars)   // 或由 02 管线在 ctx 里预置
if (!mode.pvp_enabled) throw new Error(`【${mode.name}】模式下禁止攻击其他引导者`)
```
- **中性兜底**：`mode.pvp_enabled` 缺省 true ⇒ 不配模式的局行为**逐位不变**（现状全是 PvP-on）。
- 红线对齐：这是把「PVE 禁 PvP」从「god 文件里塞 `if(gametype===X)`」改成「读一个开关」。开关在描述符里，闸门在钩子点。

### 4.3 副本激活 + 专属投放（02 钩子点：joinRoom 房层 init）

`joinRoom` 现有 Phase 38 敌人投放分配段（`gameActions.js:2363-2400`，查两表→`allocateRoomNpcs`→写 `gamevars.br.roomNpcs`）扩展为：

1. 读本局 `mode_key` → 若该模式 `allow_dungeons` 且本局指定了 `dungeon_key`（存 `gamevars.dungeon_key`，由开局选择写入）→ 拉 `dungeon_npc_sets` 对应的 `npc_placement_rules`。
2. **合并投放输入**：常规全图规则 ∪ 副本专属规则，一起喂 `allocateRoomNpcs`。`fixed_room_id` 非空的规则走「固定房」短路（在 `npcPlacement.js:106` 的逐规则循环里：有 `fixedRoomId` ⇒ 跳采样直接 push）。
3. 把激活的 `dungeon_key` + boss npc_id 列表写进 `gamevars.dungeon`（运行期状态位，供 §4.4 胜负判定读）。

> **零回归**：未指定副本的局，第 1 步空集 ⇒ 投放输入 = 现状常规规则 ⇒ `roomNpcs` 逐项不变。

### 4.4 副本胜负判定（02 钩子点：lifecycle + on_kill_npc 事件）

- **`evaluateDungeonClear(gamevars, dungeon)`**（新增纯函数 `src/lib/server/dungeon.js`，禁 eval）：按 `clear_condition.type` 分支读 `gamevars` 状态（击杀记录 / 当前相位 / 玩家所在房）返回 `{ cleared, failed }`。
- **接入点 A（击杀触发）**：NPC 死亡已走 `createNpcCorpse` 路径；在 NPC 死亡结算处记 `gamevars.dungeon.killedNpcIds.push(npcId)`，然后调 `evaluateDungeonClear`，命中 `kill_npc/kill_all` ⇒ 写 `gamevars.endingResult`（若 `dungeon.ending_key` 有）或直接置「副本通关」win-state。
- **接入点 B（相位/lifecycle）**：`applyRoomLifecycle`（`roomState.js:397`）已读 `endingResult` 结束局（`:411-419`）。副本「活到相位 N / 保护目标」类条件在此处补判（lifecycle 每次 persist 都跑）。复用现有结局管线发奖（`clear_rewards` 接 `endings.rewards` 同格式）。
- **奖励倍率**：撤离结算处读 `mode.reward_mult` 乘到撤离奖励上（现 `extractPlayer`，`gameActions.js:3283`）。缺省 1.0 ⇒ 不变。

## §5 分阶段落地步骤（每步可独立上线·标先后）

> 总原则：**先描述符表 + 中性读取（零行为变化）→ 再逐开关接钩子 → 再副本 → 最后 teardown**。每步空配置时行为逐位不变。

### Phase 04-1 — `game_modes` schema + 中性归一（最小可先落地）
- migration：建 `game_modes` + `rooms.mode_key` 列 + seed 2 行（pve/pvpve）。
- 新 `src/lib/server/modes.js`：`resolveMode`（缓存 + 中性默认）。**只读不接任何钩子** ⇒ 上线后行为 0 变化。
- 风险：低（纯加表 + 一个读函数，无运行端行为接入）。

### Phase 04-2 — PvP 闸门接入
- `resolvePlayerAttackAction` 加 `mode.pvp_enabled` 守卫（缺省 true 中性）。
- `🎚 模式` tab（GameModesTab）authoring + 开局/建房选模式写 `rooms.mode_key`。
- 灰度：先只对显式标 `mode_key='pve'` 的局生效；未标局走中性（全 PvP-on）。
- 风险：中（首次让模式影响真实战斗行为；但守卫只在新增开关为 false 时拒绝）。

### Phase 04-3 — `dungeon_templates` + `dungeon_npc_sets` schema + DungeonsTab authoring
- migration：建两表（中性默认：combat_mods 缺省 1.0 / 条件空 / 无 reward）。
- `🏰 副本` tab：副本 authoring（胜负条件构建器 + 引用 placement 规则 + 固定 boss 房）。
- **不接运行端** ⇒ 上线后行为 0 变化（副本表存在但无局激活）。
- 风险：低（纯加表 + authoring UI）。

### Phase 04-4 — 副本运行端激活（专属投放 + 胜负判定）
- `joinRoom` 投放段合并副本规则（`fixed_room_id` 短路）；写 `gamevars.dungeon`。
- `evaluateDungeonClear` 纯函数 + 接入 NPC 死亡结算 + `applyRoomLifecycle` + 撤离奖励倍率。
- `combat_mods` 乘区接入 `resolveNpcCombatProfile` / calcDamage 上游（DEFAULT 1.0 中性，呼应 Phase 37 铁律）。
- 灰度：只对显式 `gamevars.dungeon_key` 的局生效；其余局空集 ⇒ 逐项不变。
- 风险：中（改投放合并 + 战斗乘区；中性默认守底）。

### Phase 04-5 — `br_match*` 第二实现 + chamber 死分支 teardown
- 删 `/br` 页 / `api/br/route.js` / 纯 br_match server 模块 / `advanceChamber` 分支。
- 单独 teardown migration 删四表（确认零引用后）。
- 风险：中（删代码风险；逐步删、先核引用、最后删表，独立可回滚）。

## §6 安全 / 中性 / 迁移兜底

- **空配置中性（Phase 37 铁律）**：`game_modes.pvp_enabled` DEFAULT true、`combat_mods` 缺省全 1.0、`reward_mult` DEFAULT 1.0、`dungeon` 条件空集 ⇒ **不配任何描述符的局，战斗 / PvP / 投放 / 奖励逐值不变**。每条 migration 验证查询含「现有局新列全中性」断言（仿 `phase-37-unified-combat.sql:131-144`）。
- **向后兼容**：`rooms.mode_key` NULL ⇒ `resolveMode` 按 `gamevars.br` 推默认。在飞局（已有 `gamevars`、无 mode_key）继续按现状跑到本局结束，不中途变结构（同 `joinRoom` 现有「不中途变结构」原则，`gameActions.js:2423`）。
- **引用完整性（红线）**：副本→NPC、副本→placement 规则、模式→局 全用 ID / 业务键软引用 + 引用校验，DungeonsTab 保存时干跑校验「通关 boss 是否会刷出」「奖励道具是否存在」。删 NPC / 删规则 走 `ON DELETE CASCADE`（`dungeon_npc_sets`）—— 绝不 dts 名串匹配。
- **确定性**：副本专属投放复用 `allocateRoomNpcs` 的种子 PRNG（`hashSeed(seed,'npcplace:'+rule.id)`）；`fixed_room_id` 短路是确定性的（无随机）⇒ 同 seed 同结果，不破 BR 重放一致。
- **灰度**：每个行为接入步（04-2 PvP 闸门 / 04-4 副本）都先「仅显式标记的局生效」，未标局走中性，可随时回滚到上一 Phase。
- **不部署**：所有 migration 只写不跑，主代理审后用 postgres MCP 执行（沿用 phase-33/34/36/38 模式）。
- **teardown 安全**：先删页/API（用户面）→ 核实 server 模块引用 → 最后删表；每步独立 commit，删表前用 `grep` 全仓核零运行引用。

## §7 留给用户的开放决策

1. **PVPVE 是「全程可 PvP」还是「分相位开放」？** 现 `pvp_enabled` 是布尔全局开关。若要「前期禁、缩到内圈才开 PvP」，需把 `pvp_enabled` 升级为 `pvp_from_phase int`（接 `getBrEffectivePhase`）。先做布尔，还是一步到位相位门？
2. **副本怎么进入？** （a）开局选房时选副本（写 `rooms.mode_key + gamevars.dungeon_key`）；（b）局内抵达「副本入口房」触发；（c）事件 `event_pool` 的 effect 触发。本设计默认 (a)，是否要 (b)/(c)？
3. **`win_condition='dungeon_clear'` 与多人「最后一人存活」如何并存？** PVPVE 副本里：是「打完 boss 全员通关」还是「打完 boss 后还要互相撤离竞争」？影响 §4.4 判定优先级。
4. **chamber_templates 何时彻底退役（D-2）？** `docs/unified-combat-npc-design.md:84` 列了迁参数 / 改键 / 删表的高风险步骤。本子系统的副本投放跑通后，是否启动 D-2，还是继续留 chamber 作物品过程化兜底？
5. **副本掉落 vs 全图掉落的关系。** 副本专属 NPC 的掉落走 NPC `item_slots`（Phase 37 已有）；`dungeon.clear_rewards` 是额外通关奖。两者是否要做「副本内禁全图常规掉落」的开关，还是叠加？
6. **`combat_mods` 作用域。** 副本战斗乘区只作用于副本专属 NPC，还是该房 / 该局所有战斗（含 PvP）？影响接入点（`resolveNpcCombatProfile` vs `calcDamage` 全局）。
