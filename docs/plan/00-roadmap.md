> 📌 **状态注记（2026-07-04）**：01 内容引擎 ✅（Phase A 及后续 hub 收编均落地）；02 战斗管线 **P0-P4.5 全部完成 ✅**（剩 P6 死事件）；03 合成链 **运行时+局内 UI ✅**（item_recipes 可玩闭环·RLS 收紧移交 🔒 安全性轨=下方决策 2 的落地形态·局外回港合成用户拍板不做）；04/05/06 未启动（守既定顺序）。下方决策 1（集卡 vs 残片）与 3（inventory 模型）仍待拍板。执行组织已转为 4 并行轨道（见 `07-parallel-tracks.md`）。

> 来源：对 dts(《常磐大逃杀》·成熟 PHP 文字 BR·1555 commits) 与 DTSV(本项目) 的全方位对比反思。
> 核心结论：dts 能堆出 305 技能 / 382 配方 / 多副本，靠的不是「写了这些功能」，而是**「内容=数据 + 引擎加法消费 + 有工具写数据」**这套管线。DTSV 重构时**保留了野心、却把这套可扩展性丢了**——于是有 gameActions 上帝文件、8-perk 白名单、半成品/烂尾系统散落。
> 用户拍板方向：① 后台「易写的内容编辑引擎」是主轴(内容用户自己写) ② 只做 搜打撤 PVE + PVPVE ③ 顺序 道具→…→技能树 ④ 集卡/成就倾向回归 dts 清晰模型(残片太难懂) ⑤ 只取 dts 意图·落地 DTSV 原生(Postgres/JSONB/JS·ID 引用·守 Phase 37 中性铁律)。

## 反直觉的全局发现
反思中最重要的一点：**「移植 dts」大多其实是「补完 DTSV 自己起了头又烂尾的系统」**，而非从 PHP 搬代码——
- **合成链**：引擎 + 玩家 UI(CraftModal) + 后台编辑器 + 服务端分发**全写好了**，`tier_recipes`/`recipe_ingredients` 表也**已存在**，只差 RLS 修复 + 零配方 + 3 个引擎 bug。
- **战斗技能**：`passive_skills` 表 + `triggerPassives` 分发 + `evalFormula` 沙箱 + admin 编辑器**都在**，只差「有序阶段伤害管线」+ 4 个死事件接线。
- **多模式**：「只做 PVE+PVPVE」+「孤立 br_match* 待 teardown」都是**项目自己已记录的决定**。
> ⇒ 投入产出极高：大量是「收尾」而非「新建」。

## 依赖图（决定顺序）

```
        ┌─ 01 后台内容引擎 ──(authoring 地基)──┐
        │                                      ├─→ 03 合成链 ─→ 06 技能树
        └─ 02 战斗钩子管线 ──(运行地基)────────┤        ↑(用户拍板:道具先,技能后)
                                               └─→ 04 副本/NPC ─→ 05 集卡/成就(效果)
```
- **01 后台内容引擎** + **02 战斗钩子管线** 是两块地基，先行。
- **03 合成链** 依赖 01(轻)/02(弱)——可最早见效(补完烂尾)。
- **04 副本/NPC** 依赖 01+02。**05 集卡/成就** 依赖 01+02(+03/04 供收集对象)。**06 技能树** 依赖 02(必须先有)+排在 03 之后。

## ⚠️ 需要你拍板的跨切面决策

1. **集卡/成就 vs 残片**（最大·见 `05-collection-achievement.md` §9）——
   - **A(轻·推荐)**：残片全保留，仅在 /codex 叠一层清晰的「集卡/成就 + 差一张就集齐 + 达成给收益」，零叙事影响。
   - **B(中)**：残片降为纯叙事收藏，新增独立集卡/成就数值层。
   - **C(重)**：残片并入集卡套牌，废弃知识图谱/悬案。
2. **RLS / 安全收紧时机**——03 的合成表 RLS 修复是「全库 RLS 全关 + 后台 anon 直写」这个系统性安全洞的一部分(见之前安全审计 4/10)。是借 03 顺手把内容表 RLS 立起来当试点，还是先单独做一轮安全收紧？
3. **inventory 数据模型**——道具背包现为 `string[]`(名数组)，合成/集卡长期需 `{item_id,count}[]`。何时升级(短期可 id↔name 桥接兼容)。
