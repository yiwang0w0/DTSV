# 01 · 后台内容编辑引擎（Admin Content-Authoring Engine · 主轴地基）

> 状态：实现级设计文档（design doc，**只写不跑**）。
> 作者视角：DTSV / 远星函馆 系统规划 agent。
> 依赖图定位：本子系统是 **03（合成链 / 副本）/ 04（NPC·技能）/ 06（集卡·成就）** 的 **authoring 地基**；
> 不依赖 02（战斗钩子管线），但与 02 在运行端通过「ID 引用 + 中性回落」解耦协作。
> 红线：移植仅取 dts 的设计**意图**，落地 100% DTSV 原生（Next.js 14 / Supabase / Postgres / JSONB / JS 纯函数）。
> 引用一律 **ID + 引用完整性**，杜绝 dts「改名即断链」。战斗改动守 Phase 37「空配置 ⇒ 数值逐值不变」中性铁律。

## ① 目标与范围

### 1.1 一句话目标
把当前 admin **20 个手写 tab**（`src/app/admin/page.js:29-50` 的 `TABS` 数组）背后大量重复的 CRUD 脚手架，收口成一个
**schema 驱动的「内容类型描述符」 + 一个通用编辑器引擎组件**：新增一种可填表内容（合成配方 / 副本 / NPC / 技能 / 集卡 / 成就）
只需「声明一份 schema」，而非再 copy-paste 一个 400 行的 `*.jsx` tab。

### 1.2 为什么是主轴（用户已拍板）
- 用户内容**自己写**，平台只提供成熟好用的 authoring 工具。引擎是「易写」这件事的载体。
- 顺序硬约束：**道具（合成链）先 → 技能树排其后再认真做**。引擎要先把「道具 / 合成」打磨到顺手，技能树才接得上。
- 模式范围已收窄为 **搜打撤 PVE + PVPVE**，不做 dts 的 13 模式广度。引擎的内容类型只服务这两模式，不为废弃模式留字段。

### 1.3 范围内（In Scope）
1. **内容类型描述符（schema descriptor）** —— 一份纯数据声明：字段、类型、校验、引用关系、默认值、预览器、欠铺/断链警告钩子。
2. **通用编辑器引擎（`<ContentEngine schema={...}>`）** —— 列表 / 搜索 / 筛选 / 表单 Modal·Drawer / 引用选择器 / 删除二步确认 / 预览 / 欠铺警告，全部从 schema 派生。
3. **引用完整性层** —— 所有跨内容引用走 **ID（bigint/integer FK）**；编辑器侧 + DB CHECK/FK 双层防断链；提供「孤儿引用扫描」。
4. **渐进迁移路径** —— 引擎与 20 个老 tab **并存**；新内容类型直接用引擎；老 tab 逐个收口，**不大爆改**。
5. 第一批用引擎落地的内容类型：**道具合成配方（item → item 的消耗品合成）** 作为开荒样板（见 §3.4 与 §5）。

### 1.4 范围外（Out of Scope · 显式不做）
- 不重写战斗逻辑、不碰 `src/lib/gameEngine.js` / `src/lib/server/gameActions.js` 的判定（02 子系统的事）。
- 不在本子系统落地技能树的**运行时**（技能排道具之后；本期只为技能预留 schema 形状，不做消费）。
- 不动 `equipment_series → equipment_tiers → tier_recipes → recipe_ingredients` 这条**已存在且 ID 原生**的装备合成链的运行时（`src/lib/equipmentEngine.js`）；引擎只是把它的 authoring UI 逐步纳管。
- **孤立的 `br_match*` 第二实现**（`src/lib/server/br/match.js` 等）：按项目自己的记录 **teardown**，不纳入内容引擎（不为它声明 schema）。

## ② 数据模型

### 2.0 设计原则（三条铁律）
1. **引擎不需要新建「元表」就能跑**。内容类型 schema 是**前端代码里的纯数据**（`src/app/admin/_engine/schemas/*.js`），不入库。
   引擎操作的永远是各内容类型**自己的业务表**（`item_pool` / `npc_pool` / 新建的 `item_recipes` …）。
   —— 避免造一个「EAV 万能表」黑洞（那才是新的「难懂」）。
2. **引用一律 ID**。dts 的 `itemmix` 用名串数组匹配材料（`'stuff' => array('杂炊','松茸')`，见
   `D:\Fragments\_dts_clone\include\modules\base\itemmix\itemmix\config\itemmix.config.php`），改名即断链。
   DTSV 已有正确范式：`recipe_ingredients.item_id REFERENCES item_pool(id)`（见 §2.2）。本引擎强制沿用。
3. **新表幂等 + 中性默认**。所有 migration 用 `CREATE TABLE IF NOT EXISTS` / `pg_constraint` 检测后 `ADD` /
   `CREATE OR REPLACE FUNCTION` / `COMMENT`，可重复执行；任何「未铺内容」状态下，运行端读到空集即**逐值回落到现状**。
   （沿用 `scripts/phase-36-placement-rules.sql:104-284` 已验证的范式。）

### 2.1 现状盘点（已存在、引擎要纳管，不重建）
| 内容类型 | 现状表 | 现 authoring tab | 引用现状 |
|---|---|---|---|
| 道具 | `item_pool`（含 `id`、`name UNIQUE`、`kind`、`atk/def/heal/effect`、`use_mode`、`inspect_text`、`chamber_template_ids[]`、`on_use_buff_ids[]`、`*_formula`） | `ItemsTab.jsx` | `name UNIQUE`（Phase 34 §0 建立），`chamber_template_ids` 是 ID 数组 ✅ |
| 实体/NPC | `npc_pool`（`id`、`hp/atk/def/exp`、`level`、`maps[]`） | `NpcsTab.jsx` | 待核 maps 是否 ID |
| 装备系 | `equipment_series`→`equipment_tiers`→`tier_recipes`→`recipe_ingredients` | `EquipmentSeriesSection.jsx`（**最成熟范式**） | 全 ID FK ✅ |
| 残片合成 | `fragment_pool` + `fragment_combos`（`fragment_id_a/b`、`unlocks_fragment` 均 ID） | `FragmentCombosTab.jsx` | 全 ID ✅ |
| 投放规则 | `placement_rules` + `placement_rule_rooms` | `RoomItemsTab` / `usePlacementRules.js` | item 走 `name` FK、tier 走 `id` FK，房软引用 |

> 结论：装备链（`recipe_ingredients`）与残片合成（`fragment_combos`）已是 ID 原生、引用完整的正确样板。
> 引擎的工作是**把这种正确范式产品化**，让「道具消耗品合成 / 副本 / 成就 / 集卡」都按它来，而不是各写一套。

### 2.2 装备合成链回顾（引擎复用的 ID-引用样板，**不新建**）
来自 `src/lib/equipmentEngine.js:177-261` 的 `checkCanCraft` 查询契约：
```
tier_recipes ( id, result_tier_id→equipment_tiers, recipe_name, success_rate, gold_cost,
               fail_behavior, requires_prev_tier_id, requires_prev_series_id, requires_prev_tier_num )
recipe_ingredients ( id, recipe_id→tier_recipes, ingredient_type('item'|'equipment'),
                     item_id→item_pool(id), equipment_tier_id→equipment_tiers(id),
                     quantity, is_consumed, is_catalyst )
```
**已发现的一处待修隐患**（不在本期改，但 schema 设计要规避）：`equipmentEngine.js:245`
`playerInventory.filter(i => i.item_id === ing.item_id || i.name === ing.item?.name)` —— `|| i.name===…` 是
名串回落，正是红线要消灭的「改名即断链」尾巴。新建的合成表与运行端**只认 `item_id`**，不留 name 回落。

### 2.3 第一批新表 —— 道具合成（`item_recipes` + `item_recipe_ingredients`）
> WHY：装备链是「series/tier 纵向升阶」模型，重；**道具消耗品合成**（dts itemmix 的核心意图：A+B+…→C 一个新消耗品）
> 需要一张更轻的横向配方表。用户原话「道具（合成链）先」即指这条。结构刻意与 `recipe_ingredients` **同形**，
> 让引擎的「引用选择器 + 数量」组件两处复用。

```sql
-- scripts/phase-XX-item-recipes.sql （只写不跑，主代理审后用 postgres MCP 执行）
BEGIN;

-- §1 配方主表：N 个输入材料 → 1 个输出道具（均引用 item_pool.id）
CREATE TABLE IF NOT EXISTS item_recipes (
  id            bigint      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name          text        NOT NULL,                       -- 配方展示名（如「特级恢复药·合成」）
  -- 输出：合成产物（ID 引用，删道具 → 连带清配方）
  result_item_id bigint     NOT NULL REFERENCES item_pool(id) ON DELETE CASCADE,
  result_qty    integer     NOT NULL DEFAULT 1,             -- 一次合成产出几个
  -- 成功率 / 失败行为（沿用装备链语义，便于引擎统一字段组件）
  success_rate  real        NOT NULL DEFAULT 1.0,           -- [0,1]
  fail_behavior text        NOT NULL DEFAULT 'lose_materials', -- 'lose_materials'|'keep_materials'
  -- 门控（可空，空=无门控；运行端空值逐值回落「无限制」）
  req_level     integer     NULL,
  -- authoring 叙事文案（在 /archive 或合成 UI 展示）
  description   text        NULL,
  enabled       boolean     NOT NULL DEFAULT true,          -- 软开关；运行端只读 enabled=true
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

-- §2 配方材料桥接（同形于 recipe_ingredients；只认 item_id，无 name 回落）
CREATE TABLE IF NOT EXISTS item_recipe_ingredients (
  id          bigint  GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  recipe_id   bigint  NOT NULL REFERENCES item_recipes(id) ON DELETE CASCADE,
  item_id     bigint  NOT NULL REFERENCES item_pool(id) ON DELETE RESTRICT, -- 删被引用材料 → 阻塞（防断链）
  quantity    integer NOT NULL DEFAULT 1,
  is_consumed boolean NOT NULL DEFAULT true               -- false=催化剂（检查但不扣）
);

-- §3 命名 CHECK（pg_constraint 检测后 ADD ⇒ 幂等）
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='item_recipes_success_rate_range'
                 AND conrelid='item_recipes'::regclass) THEN
    ALTER TABLE item_recipes ADD CONSTRAINT item_recipes_success_rate_range
      CHECK (success_rate >= 0 AND success_rate <= 1);
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='item_recipes_result_qty_pos'
                 AND conrelid='item_recipes'::regclass) THEN
    ALTER TABLE item_recipes ADD CONSTRAINT item_recipes_result_qty_pos CHECK (result_qty >= 1);
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='item_recipe_ing_qty_pos'
                 AND conrelid='item_recipe_ingredients'::regclass) THEN
    ALTER TABLE item_recipe_ingredients ADD CONSTRAINT item_recipe_ing_qty_pos CHECK (quantity >= 1);
  END IF;
  -- 同一配方对同一材料只一行（编辑器候选可安全 delete-by-recipe → 批量 insert，沿用 usePlacementRules 范式）
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='item_recipe_ing_recipe_item_key'
                 AND conrelid='item_recipe_ingredients'::regclass) THEN
    ALTER TABLE item_recipe_ingredients ADD CONSTRAINT item_recipe_ing_recipe_item_key
      UNIQUE (recipe_id, item_id);
  END IF;
END $$;

-- §4 updated_at 触发器（独立函数名，沿用 phase-36 范式）
CREATE OR REPLACE FUNCTION item_recipes_set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at := now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;
DROP TRIGGER IF EXISTS item_recipes_set_updated_at ON item_recipes;
CREATE TRIGGER item_recipes_set_updated_at BEFORE UPDATE ON item_recipes
  FOR EACH ROW EXECUTE FUNCTION item_recipes_set_updated_at();

-- §5 索引：合成 UI 按 result / 按材料反查
CREATE INDEX IF NOT EXISTS item_recipes_by_result ON item_recipes(result_item_id);
CREATE INDEX IF NOT EXISTS item_recipe_ing_by_recipe ON item_recipe_ingredients(recipe_id);
CREATE INDEX IF NOT EXISTS item_recipe_ing_by_item ON item_recipe_ingredients(item_id);

COMMIT;
```

**RLS**：沿用现有 admin 表惯例 —— DTSV 现状是「`authenticated` 全权、RLS 关」（见 `usePlacementRules.js:10` 注释「直连 supabase（RLS 关·authenticated 全权）」）。
本期**保持一致**（写权限由前端 `isAdmin()` 闸口 + 服务端 action 控制），不单独为这两张表开 RLS，以免与全库策略割裂。
若后续全库收紧 RLS，这两张表随大流加 `FOR SELECT TO authenticated USING(true)` + 写策略限管理员，**留作开放决策（§7）**。

### 2.4 后续内容类型的 schema 形状（本期只声明、不全部建表）
- **集卡 / 成就（06 子系统，回归 dts 清晰模型）**：dts 的成就是「编号 + 类型分组 + 计数/完成条件 + 可用时段 + 允许模式」
  （见 `D:\Fragments\_dts_clone\include\modules\extra\achievement\achievement.readme.txt` 与
  `achievement_base\config\achievement_base.config.php` 的 `$achtype/$achlist/$ach_allow_mode`）。
  DTSV 原生落地：`achievement_defs (id, code UNIQUE, group_key, title, desc, trigger_kind, target_count, mode_mask, available_from, available_to, enabled)`
  + 运行进度 `player_achievements (user_id, achievement_id→achievement_defs, progress jsonb, completed_at)`。
  **关键**：dts 用「一个技能 = 一个成就」+ base64 计数串（`achievement_base/readme.txt`），是 PHP eval/名串范式；
  DTSV 改为 **`trigger_kind` 枚举 + `target_count` 数值 + `progress jsonb`**，由 02 的战斗钩子管线在事件点 `+1`，**纯数据驱动，零 eval**。
  集卡同理：`card_defs (id, code UNIQUE, pack_key, rarity, title, art_url, ...)` + `player_cards`，**不照搬 dts 名串卡池**。
- **技能（04 子系统，排道具之后）**：本期只在引擎里预留 schema 占位（字段：`code/name/tier/cost/effect_kind/effect_value/req_*`），
  **不建表、不接运行时**。等道具/合成顺手后再认真做（用户硬约束）。

## ③ 后台编辑（怎么在内容引擎里 authoring）

### 3.1 引擎目录（新增，与老 tab 隔离）
```
src/app/admin/_engine/
  ContentEngine.jsx        — 通用编辑器引擎（schema → 完整 CRUD UI）
  fields.jsx               — 字段渲染器：text/number/select/textarea/bool/ref/ref-multi/ingredient-list/formula
  useContentCrud.js        — 通用 CRUD hook（load/搜索/筛选/save/delete/候选同步），从 usePlacementRules.js 抽象升级
  refIntegrity.js          — 引用解析 + 孤儿/断链扫描（纯函数）
  schemas/
    itemRecipe.js          — 道具合成配方 schema（第一个落地，§3.4）
    ...（后续 achievement.js / card.js / skill.js）
```
**复用而非另起**：引擎的视觉/控件 **直接 import** `src/app/admin/_shared/ui.js`（`BTN/INPUT/LABEL/Modal/Drawer/DeleteBtn/Spinner/SECTION_TITLE/HINT/FormulaPreview/RARITY_META/C`）。
CRUD hook 把 `usePlacementRules.js`（`src/app/admin/_tabs/usePlacementRules.js:25-186`）已验证的
「主表 upsert + 桥接表 delete-by-parent→批量 insert + 缺表静默降级 + 前端预校验给友好 toast」模式**泛化**。

### 3.2 内容类型描述符（schema descriptor）形状
一份 schema 是纯对象，引擎据此渲染整个 tab：
```js

export default {
  key: 'itemRecipe',
  label: '🧪 道具合成',
  table: 'item_recipes',
  pk: 'id',
  searchFields: ['name', 'description'],
  filters: [{ field: 'enabled', label: '状态', options: [['all','全部'],['true','启用'],['false','禁用']] }],
  // 列表卡片摘要渲染器（可选；缺省用 fields 自动摘要）

  fields: [
    { name: 'name', type: 'text', label: '配方名', required: true,

      hint: '留空=无门槛；运行端读到 null 逐值回落「不限制」' },
    { name: 'description', type: 'textarea', label: '合成叙事', rows: 2 },
    { name: 'enabled', type: 'bool', label: '启用', default: true },

      itemFields: [
        { name: 'quantity', type: 'number', label: '数量', default: 1, min: 1 },
        { name: 'is_consumed', type: 'bool', label: '消耗', default: true },
      ],
      validate: (list) => list.length === 0 ? '至少需要一种材料' : null,
    },
  ],
  // 跨字段校验（保存前；返回错误串则中止 + 友好 toast）
  validate: (row) => {
    if (row.ingredients?.some(i => i.item_id === row.result_item_id))
      return '材料不能与产出是同一道具（防自指环）'
    return null
  },
  // 预览：用现有 evalFormula/FormulaPreview 同款即时反馈
  preview: (row, refs) => ({ kind: 'recipe', inputs: row.ingredients, output: row.result_item_id }),
  // 欠铺/断链警告钩子（见 §3.5）
  warnings: ['orphanRefs', 'emptyIngredients', 'unreachableResult'],
```

### 3.3 引擎渲染出的 UI（每个内容类型自动得到）
1. **顶栏**：搜索框（`searchFields`）+ 筛选 chips（`filters`）+「+ 新增」按钮 —— 复刻 `ItemsTab.jsx:116-128` 的布局。
2. **列表**：卡片网格，`summary` 渲染摘要，右上角「编辑 / 删除（二步确认，复用 `DeleteBtn`）」。
3. **表单**：Modal（少字段）或 Drawer（多字段/含桥接，复用 `EquipmentSeriesSection` 的 Drawer 范式）；
   字段按 `fields` 顺序渲染，`type` 决定控件（见 §3.4 控件表）。
4. **引用选择器（`type:'ref'` / `'ref-multi'`）**：下拉/可搜列表，**option 显示 `[id] name`、value 存 id**（沿用 `FragmentCombosTab.jsx:181-184`）。
   引擎在加载时一次性拉取被引用表（`Promise.all`），构 `id→row` map 供 `refs.<table>(id)` 解析展示名 —— **展示名变了也不影响引用**。
5. **材料清单（`type:'ingredient-list'`）**：「+ 加材料」→ 引用选择器选道具 + 数量 + 催化剂开关；保存时桥接表 delete-by-parent → 批量 insert（同 `usePlacementRules.js:156-163`）。
6. **预览**：道具/装备数值用 `FormulaPreview`（`_shared/ui.js:110-124`）即时算；合成配方预览「材料 → 产出」链路。

### 3.4 字段类型 → 控件映射（`fields.jsx`）
| type | 控件 | 校验 | 备注 |
|---|---|---|---|
| `text` / `textarea` | `<input>` / `<textarea style=INPUT>` | required / maxLen | |
| `number` | `<input type=number>` | min/max/step、`nullable` 允许空→null | |
| `select` | `<select>` | 值必属 options | enum 字段，前端与 DB CHECK 同口径 |
| `bool` | toggle | — | |
| `ref` | 可搜下拉，显示 `[id] label` | required、**目标存在性**（断链时红框） | value=id |
| `ref-multi` | chip 多选（复用 `ItemsTab.jsx:319-329` chamber 选择器范式） | — | value=id[] |
| `ingredient-list` | 行编辑器（ref + number + bool） | 非空、无自指 | 桥接表 |
| `formula` | mono `<input>` + `FormulaPreview` | `evalFormula` 不报错 | 复用现有沙箱求值器 |

### 3.5 校验与欠铺/断链警告（authoring 时就拦住坑）
- **前端预校验**（保存前）：field 级（required/min/max/enum）+ 跨字段 `schema.validate` + 桥接 `field.validate`。
  与 DB CHECK 同口径，给**友好 toast** 而非 DB 报错（沿用 `usePlacementRules.js:115-117`）。
- **断链扫描（`refIntegrity.js`）**：加载列表后，对每行的每个 `ref/ref-multi` 字段检查目标 id 是否存在于引用表；
  孤儿引用在卡片上标红 chip「引用已失效 #id」。提供「全表孤儿扫描」按钮（一次性汇总）。
- **欠铺警告**：schema 声明 `warnings`，引擎跑对应纯函数 —— 如 `emptyIngredients`（配方无材料）、
  `unreachableResult`（产出道具未被任何投放规则铺到全图 ⇒ 玩家拿不到材料，永远合不出）。复刻 `RoomItemsTab` 的「欠铺」体感。

### 3.6 渐进迁移（不大爆改）
- 引擎首发只挂**一个新 tab**：`{ key:'itemrecipe', label:'🧪 道具合成' }` 加进 `page.js:29-50` 的 `TABS`，
  渲染 `<ContentEngine schema={itemRecipe} toast={toast} />`。老 20 tab **一行不改**。
- 验证引擎顺手后，逐个把老 tab 的 schema 化（`FragmentCombosTab` → `combos.js` schema 是最佳第二个，因它已是纯 ID CRUD）。
  每收口一个 = 删一个 `*.jsx`、加一份 schema，**净减代码**。`ItemsTab` 因有 use_mode/inspect/formula/buff/chamber 多段，排后面。

## ④ 运行端集成（DTSV 哪个文件怎么消费这些数据）

### 4.1 消费点：道具合成（新建一条服务端 action，复刻装备合成范式）
- **读取契约**：运行端按 `result_item_id` / 或列出全部 `enabled=true` 配方 + 材料，**只 `select` ID**，永不按 name。
- **新文件**：`src/lib/server/itemCraft.js`，函数 `checkCanCraftItem(recipeId, inventoryById, playerLevel, client)` /
  `executeCraftItem(recipeId, ownerId, roomId, gamevars, client)`，**逐行对照** `equipmentEngine.js` 的
  `checkCanCraft`（`:177-261`）/`executeCraft`（`:277-`）写，但材料匹配**只认 `i.item_id === ing.item_id`**（删掉 name 回落）。
- **接线点**：现有 `src/app/game/[id]/CraftModal.jsx`（装备合成）旁加「道具合成」分页，或新增 `ItemCraftModal`；
  实际扣材料/发产出走 server action（不在客户端改 `gamevars`），与现有合成同一条「掷骰 → 成功发 / 失败按 `fail_behavior`」路径。
- **库存模型对齐**：现状 inventory 是 `string[]`（道具名数组，见 `CraftModal.jsx:8-14` `buildInventoryMap`）。
  **过渡兼容**：`executeCraftItem` 扣材料时把配方的 `item_id` → 解析出 `item_pool.name` 再在名数组里扣（**仅运行末端这一处做 id↔name 桥接**，配方本身全 ID）。
  长期开放决策：inventory 升级为 `{item_id,count}[]`（§7）。

### 4.2 中性铁律落地（空配置 ⇒ 现状逐值不变）
- `item_recipes` 表**空 / 全 disabled** ⇒ 合成 UI 列表为空 ⇒ 玩家无可合成项 ⇒ **与现状（没有道具合成）完全一致**。
- 不灌任何配方数据（migration 0 行）。运行端任何「读配方」分支在空集时**直接 return 现有路径**，不改一个数值。
- 与 02 战斗钩子管线的协作（成就/集卡计数）同理：`achievement_defs` 空 ⇒ 钩子点 `+1` 找不到目标 ⇒ no-op，战斗数值零触碰（守 Phase 37 铁律）。

### 4.3 引用完整性在运行端的兜底
- `item_recipe_ingredients.item_id` 是 `ON DELETE RESTRICT`：删一个仍被配方引用的道具会被 DB 阻塞 ⇒ 运行端永远读不到悬空材料引用。
- `result_item_id` 是 `ON DELETE CASCADE`：删产出道具 → 配方自动消失 ⇒ 不会留「产出不存在」的死配方。
- 运行端读到的每个 id 都保证有对应行（FK 保证），**无需运行时再做名串模糊匹配**。

## ⑤ 分阶段落地步骤（每步可独立上线 · 标明先后）

## ⑥ 安全 / 中性 / 迁移兜底

- **向后兼容**：只**新增**表/文件/tab，零 DROP、零改现有列、零改 `gameEngine.js`/`gameActions.js` 判定。
  老 20 tab 与运行端在 Phase A–D 全程不变。
- **空配置中性**：`item_recipes` 空或全 disabled ⇒ 行为 == 现状（无道具合成）。守 Phase 37「空配置 ⇒ 数值逐值不变」。
- **幂等 migration**：`IF NOT EXISTS` + `pg_constraint` 检测 + `CREATE OR REPLACE` + `DROP TRIGGER IF EXISTS`，可重复执行（沿用 phase-36 已验证范式）。
- **只写不跑**：本设计与配套 SQL **只写文件**，由主代理审后经 postgres MCP 执行（参考 phase-33/34/36 流程）。
- **引用完整性硬约束**：材料 `ON DELETE RESTRICT`（防悬空）、产出 `ON DELETE CASCADE`（防死配方）、`UNIQUE(recipe_id,item_id)`（防重）。
- **权限**：写操作前端走 `isAdmin()`（`src/lib/auth.js`）闸口；运行端合成走 server action，不信任客户端 gamevars。
- **灰度**：运行端消费（Phase D）才改玩家行为，前面 A–C 都是「填数据不生效」，可随时停在任一 Phase。
- **红线复核**：无 PHP/eval（公式仍走现有 `evalFormula` 白名单沙箱 `gameEngine.js:16-52`）、无全局变量、无名串匹配（材料只认 id）、无 MyISAM（Postgres）。
- **`br_match*` teardown**：本子系统**不为 `br_match*` 声明 schema、不纳管**；其退役按项目自己的记录单独处理，与本引擎解耦。

## ⑦ 留给用户的开放决策

1. **inventory 数据模型升级时机**：现状道具背包是 `string[]`（名数组）。道具合成短期靠「运行末端 id→name 桥接」兼容，
   但长期断链隐患仍在（同名道具、改名）。是否在 Phase D 一并把 inventory 升级为 `{item_id,count}[]`？（牵涉面较大，需单独评估。）
2. **RLS 策略**：两张新表本期随大流「RLS 关 + 前端/服务端闸口」。是否本期就为内容表立 RLS（SELECT 公开、写限 admin）作为收紧全库 RLS 的试点？
3. **道具合成 vs 装备合成是否合并 UI**：两条链结构同形。是在 `CraftModal` 加分页（轻），还是合成一个「统一合成台」（重，但更「易用」）？
4. **集卡/成就回归 dts 模型的边界**：dts 成就深度绑定其「技能系统 + 模式编号 + 活动时段」。DTSV 只做搜打撤 PVE/PVPVE，
   `mode_mask` 只需 2 位。是否要保留 dts 的「活动时段（`available_from/to`）」与「分组（`group_key`）」维度，还是先做最简「计数型成就」？
5. **欠铺警告的强度**：`unreachableResult`（合成产物的材料没被投放规则铺到图里）是**硬拦保存**还是**软提示**？硬拦更安全但可能挡住「故意暂留半成品配方」的工作流。
6. **schema 描述符的存放**：本设计把 schema 放在**前端代码**（纯数据、随版本走）。是否未来要支持「在后台 UI 里改 schema」（meta-authoring）？那会引入元表，复杂度陡增 —— 建议明确**本期不做**。
