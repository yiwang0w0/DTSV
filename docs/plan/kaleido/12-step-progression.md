## 1. step 是什么

> 「我们设置的 step 检测,是比如玩家**第一次到达某个安全区/基地**来给他的账户从 step0 标记改为 step1;另外比如是他**杀死了某个特定敌人**、**第一次获得了某个特定物品**、**做了某个特定操作**,给他推进 step。」(Kanata)

**step = 账号级里程碑标记,由具名世界事件推进。**

- **不是**「阶段」——不按时长、不按关数、不按进度百分比
- **不是**存档系统 —— 见 §3
- 触发面 = 四类具名事件:**到达某地 / 杀死某敌 / 获得某物 / 做某操作**
- **一次性**:每个 step 只推进一次,幂等

### 1.1 已定内容

| step | 达成条件 | 备注 |
|---|---|---|
| **step0** | 注册 → 登录 → **首次搜索** | 账号首次只一次。觉醒行「很久没有回音了」**只播这一次**;再进走「延续」分支 |
| **step1** | **首次到达某个安全区 / 基地**(叙事上 = 确立第一个安全屋) | 机制上 step0→1 期间**每次搜索同步掉 HP**(负伤 buff),首要目标活下来 · 找药;由此引出物品栏 + 详细状态 UI |
| step2+ | 未定 | **不必是「安全屋→安全屋」** —— 可以是「杀掉墙后面那个东西」「第一次拿到某个物件」。里程碑形状跟着剧情走,不被地理结构绑死 |

### 1.2 死亡语义

- **死亡从当前 step 的开头重开**,且**换视角** —— 「讲的不是一个个体的故事」:上一个单位死了,下一个被派出,叙事交代「离上一个人出发过去了多久」。
- **死亡 = 时间推进,不是回档。**
- ⟹ **`step` 不随死亡回滚**(故事进度)。

## 2. 🎁 step 与 `ui_unlocks` 是同一台机器

| | `ui_unlocks` | `step` |
|---|---|---|
| 判据 | 路由边界 `beforeMe`/`afterMe` 前后态 diff | **同** |
| 存储 | 账号级 | **同** |
| 幂等 | 每键至多一次(`already.has` 早退) | **同** |
| 注册表 | `KALEIDO_UI_UNLOCKS` 15 条 `{verb, condition}` | **第二张表** |

⟹ `evaluateUnlocks` + `applyKaleidoPostAction` + 账号持久 + 幂等**整套可复用**。机制部分几乎不用新建,**成本主要在注册表内容**。

> **但不为复用而复用**:若共用 evaluator 会把 `ui_unlocks` 已稳住的逻辑搅浑,就分开写。以 🔧 实测为准。

**分工**:机制与形状 = 🔧;里程碑**语义** = 📖;**具体实体**(哪个敌人 / 哪个物品 / 哪个操作)= ⚙️。

## 3. ⚠ step 推进 ≠ 存档点提交 —— 三条独立的作用域

「首次到达安全区」那一拍是**多件事同时发生**,但它们频率与回滚语义都不同:

| 概念 | 触发 | 频率 | 死亡时 | 载体 |
|---|---|---|---|---|
| **step 推进** | 首次达成条件 | **一次性**(里程碑) | **不回滚** | 账号级 step 标记 |
| **存档点提交** | **每次**回到安全区 | **反复**(死区逼玩家每天回) | 提交点不回滚;**未提交的进度回滚** | `uiCommitted` → `profiles.ui_unlocks` |
| **场景状态** | 玩家操作场景(`operate`) | 每次 | **不回滚** | 独立持久层;日常档每日结构重置,永久白名单不重置 |

**第二次之后到达安全区,只有存档点提交,step 不动。**

### 3.1 由此得出的一条自洽性

> **玩家可能是 step3,却顶着 step1 的 UI 集。这不是 bug。**

- `step` = **故事走到哪儿了**
- UI 解锁 = **这个单位知道什么**

⟹ 「故事在前进,人换了一茬」的机制表达。**实现里不得把这两者对齐**,它们本来就该错位。

### 3.2 回滚语义相反的东西不得共用字段

`step`(永不回滚)与 `ui_unlocks`(随存档点回滚)**必须分开存**。同 `11 §3.1.4` 的教训(UI 解锁持久层 vs 场景状态持久层)。
